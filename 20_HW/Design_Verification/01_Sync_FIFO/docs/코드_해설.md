# Sync FIFO UVM: 코드로 따라가는 검증 환경

## 실행

Windows VS Code에서 편집하고 Ubuntu 터미널에서 아래 명령을 실행합니다.

```bash
cd /mnt/c/Users/Jiyun/Documents/coding_study/Study/20_HW/Design_Verification/01_Sync_FIFO
bash run.sh build
bash run.sh run 1 +SMOKE_ONLY +UVM_VERBOSITY=UVM_HIGH
bash run.sh run 1
bash run.sh regression
```

- build: Verilator 5.052로 UVM과 FIFO 환경을 컴파일합니다. obj_dir에 결과가 생깁니다.
- run 1: seed 1로 directed 시나리오와 랜덤 요청 200개를 실행합니다.
- +SMOKE_ONLY: 기존 nested A5 쓰기 1회/읽기 1회만 실행합니다. coverage 달성은 요구하지 않습니다.
- +UVM_VERBOSITY=UVM_HIGH: driver와 monitor의 매 사이클 관찰 로그를 표시합니다.
- +WAVES: 프로젝트 루트에 fifo.vcd를 생성합니다. 예: bash run.sh run 1 +WAVES
- regression: seed 1, 7, 42의 정상 통과와 의도적 데이터 불일치 검출을 확인합니다.
- +INJECT_MISMATCH: 첫 읽기 비교에서 비교용 예상값의 bit 0만 반전합니다. DUT 및 실제 queue는 수정하지 않습니다. 이 실행의 실패는 의도한 결과입니다.

UVM_HOME 기본 경로는 ~/tools/uvm-2020.3.1입니다. 필요하면 export UVM_HOME=...으로 변경합니다. UVM_NO_DPI로 외부 DPI 기능을 제외합니다. 파형은 추가 압축 라이브러리가 필요 없는 VCD 형식입니다.

## 전체 흐름

```text
fifo_test
  env
    agt
      sqr <-- sequence가 요청을 전달
       | get_next_item / item_done
      drv ---> fifo_if ---> DUT
                             |
      mon <----- fifo_if <---+
       | mon_ap
       +--> agt.mon_ap --> sb.mon_imp      독립 queue로 자동 비교
                      +-> cov.analysis_export   발생한 검증 상황 집계
```

## 먼저 읽을 코드 순서

1. fifo_sequence.sv: 기존 write/read 자식 sequence를 start(m_sequencer, this)로 실행합니다. 이 파일과 자식 두 파일은 보존했습니다.
2. fifo_driver.sv: 한 item을 받아 한 상승 에지 동안 적용합니다. do_reset item이면 apply_reset()을 호출합니다. reset의 단일 구동 주체는 driver입니다.
3. fifo_monitor.sv: 상승 에지에서 요청과 처리 전 flag를 저장하고, 다음 하강 에지에서 응답과 처리 후 flag를 저장합니다. 매번 새 item을 analysis port로 전송합니다.
4. fifo_scoreboard.sv: monitor의 실제 관찰값으로 독립 예상 queue를 갱신하고 rdata와 flag를 검사합니다.
5. fifo_env.sv: agent의 analysis port를 scoreboard와 coverage 양쪽으로 연결합니다.
6. fifo_test.sv: sequence 실행 후 마지막 요청이 scoreboard에서 처리될 때까지 기다린 다음 objection을 내립니다.
7. fifo_regression_sequence.sv: 경계, wrap, reset, 랜덤 요청을 구체적인 코드로 확인합니다.

## 새로 추가한 파일

| 파일 | 역할 |
| --- | --- |
| tb/fifo_scoreboard.sv | queue 기반 예상 모델, 읽기 순서·출력 유지·reset·처리 전후 flag 검사, 종료 시 미처리 데이터 확인 |
| tb/fifo_coverage.sv | 상태 3개 × 요청 4개, reset 당시 상태 3개, write/read wrap 발생을 집계하는 기능 coverage 카운터 |
| tb/fifo_regression_sequence.sv | directed 경계 요청, 반복 fill/drain, 부분/full/empty reset, 랜덤 요청 200개, 마지막 drain |
| tb/fifo_assertions.sv | full/empty 동시 활성 금지, reset 값, 포인터 증분·유지, 읽기 없는 rdata 유지 검사 |
| run.sh | 빌드·seed 실행·회귀·오류 주입 검사와 로그 저장 |

## 기존 파일에서 바뀐 점

- item: do_reset, rst_n, full_after/empty_after, request_id를 추가했습니다. wr_en/rd_en/wdata만 rand입니다.
- interface: request_id는 테스트벤치 전용 식별자이며 DUT에는 연결하지 않습니다.
- driver: 초기 reset과 재reset을 직접 구동합니다. completed_count로 완료한 item 수를 기록합니다. 같은 요청을 반복 구동하지 않도록 다음 하강 에지에서 enable을 내립니다.
- monitor: reset 중에도 관찰값을 전송하여 모델을 비웁니다. full/empty는 처리 전, full_after/empty_after와 rdata는 처리 후 값입니다.
- env: scoreboard와 coverage를 생성하고 agent의 analysis port에 연결했습니다.
- test: SMOKE_ONLY 또는 전체 시나리오를 선택합니다. item_done만으로 종료하지 않고 scoreboard.last_processed_id를 기다립니다.
- top: reset 구동을 driver로 옮겼습니다. assertion 인스턴스, 선택적 VCD 출력, 100us timeout을 연결했습니다.
- package: 추가 클래스들을 의존 순서대로 포함합니다.

DUT RTL은 수정하지 않았습니다.

## queue가 예상값을 만드는 방법

예를 들어 queue가 [A, B]이고 write/read가 동시에 들어오면:

1. 처리 전 크기 2로 write와 read 모두 수락 가능하다고 판단합니다.
2. pop_front()의 A를 expected_rdata로 보관합니다.
3. 새 wdata C를 push_back()해서 queue는 [B, C]가 됩니다.
4. 실제 rdata가 A인지, 처리 후 flag가 queue 크기와 맞는지 검사합니다.

full 상태에서는 동시 요청이라도 write가 거부되고 read만 수락됩니다. empty 상태에서는 write만 수락되고 read는 거부됩니다. 수락 결정 둘 모두 처리 전 크기를 사용합니다. pop 후 push라는 모델 코드 순서가 하드웨어 동작 순서를 뜻하지 않습니다.

예상 데이터는 오직 수락된 wdata에서 나옵니다. 실제 rdata는 예상 queue에 넣지 않습니다. 읽기 없는 사이클에는 마지막 출력 유지 여부도 검사합니다.

## sampling 시점

```text
negedge          posedge                       negedge
DRV 입력 구동 -> MON 요청/flag(pre) 저장 -> MON 응답/flag(post) 저장
                 DUT NBA에서 상태 갱신          analysis.write -> 비교
```

driver는 하강 에지에서 NBA 대입을 사용합니다. monitor가 같은 하강 에지에서 읽는 동안에는 이전 요청이 유지됩니다. 하강 에지 사이에 하나의 상승 에지가 있으므로 읽기 응답과 요청을 매칭할 수 있습니다. request_id는 비교 완료를 추적하기 위한 표식이며 예상 데이터의 출처가 아닙니다.

## 완료 조건과 오류 검출

sequence의 finish_item은 driver의 item_done까지 기다립니다. monitor는 같은 하강 에지에서 아직 관찰값을 전달 중일 수 있으므로 test는 scoreboard가 마지막 id를 처리할 때까지 별도로 기다립니다. 종료 시 queue가 비었는지, 비교가 1건 이상인지 확인합니다. 전역 timeout이 누락된 handshake로 인한 무한 대기를 잡습니다.

정상 실행은 [RESULT] FIFO verification PASS를 남겨야 합니다. run.sh는 시뮬레이터의 프로세스 반환 코드만 믿지 않고 이 표시도 확인합니다. 오류 주입 실행에서는 [DATA] mismatch와 실패를 확인합니다. 단순히 오류가 없거나 coverage bin이 채워졌다는 이유만으로 통과시키지 않습니다.

## 범위와 한계

- 현재 구성은 DATA_WIDTH=32, FIFO_DEPTH=4 전용입니다. DUT의 포인터 구조상 깊이는 2의 거듭제곱이어야 합니다. 파라미터 sweep은 구현하지 않았습니다.
- 기능 coverage는 명시적 카운터이며 covergroup/UCIS DB나 RTL code coverage가 아닙니다. 12개 bin 달성은 정의한 상황 발생만 의미합니다.
- reset 시나리오는 요청 사이 하강 에지에 시작하고 3클럭 유지합니다. 임의의 짧은 비동기 reset pulse와 전송 도중 reset 취소는 후속 실습입니다.
- Verilator의 X/Z 동작과 UVM_NO_DPI 환경은 4-state 상용 시뮬레이터와 동일하다고 보지 않습니다.
- 오류 주입은 scoreboard 비교 경로의 검출 여부를 확인합니다. 모든 assertion을 의도적 DUT 결함으로 검증한 것은 아닙니다.
- build warnings와 UVM warnings는 로그로 보존하고 실행 결과 문서에서 해석합니다.
