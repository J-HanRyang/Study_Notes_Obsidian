# 기본 코드 해설: 입력을 저장하고 출력을 비교하기

## 범위

기존 driver·monitor·sequence를 사용합니다. 현재 sequence는 A5 쓰기 한 번, 읽기 한 번입니다. 추가한 주요 클래스는 scoreboard와 coverage 두 개입니다. assertion 등 확장 코드는 tb_extend에 보관했습니다.

## 연결

```text
sequence → sequencer → driver → FIFO
                                 ↓
                              monitor
                                 ↓
                         agent.mon_ap
                           ├─ scoreboard.mon_imp
                           └─ coverage.analysis_export
```

새 클래스는 env에서 생성하고 connect_phase에서 agent의 analysis port에 연결합니다. monitor에서 mon_ap.write(fifo_item)을 호출하면 두 수신자의 write() 함수가 실행됩니다. 새 transaction 생성·수집 방식은 원래 monitor를 유지했습니다.

## scoreboard — fifo_scoreboard.sv

예상 데이터는 queue에 저장합니다.

```systemverilog
bit [31:0] expected_q[$];
```

쓰기 요청이 수락되면 입력 데이터를 queue 끝에 넣습니다.

```systemverilog
if (fifo_item.wr_en && !fifo_item.full)
    expected_q.push_back(fifo_item.wdata);
```

읽기 요청이 수락되면 queue 맨 앞 데이터를 꺼내 실제 출력과 비교합니다.

```systemverilog
expected_data = expected_q.pop_front();
if (fifo_item.rdata !== expected_data)
    // UVM_ERROR
```

실제 코드는 읽기 수락 조건과 queue가 비어 있지 않은지도 확인합니다. 같은 클럭에 쓰기·읽기가 모두 수락되면 기존 맨 앞 데이터를 먼저 비교한 후 새 데이터를 넣습니다. 수락 여부는 monitor가 관찰한 처리 전 full/empty로 판단합니다. 이번 단계는 데이터 비교에 집중하며, full/empty 자체의 정확성을 독립 검사하지는 않습니다.

check_phase는 비교가 실제로 발생했는지, 종료 시 예상 데이터가 남지 않았는지만 확인합니다. 처음에는 A5 한 건 비교와 queue가 비는 것까지 보면 됩니다.

## coverage — fifo_coverage.sv

우선 covergroup 문법 없이 요청 종류를 세는 간단한 카운터입니다.

```systemverilog
request_count[{fifo_item.wr_en, fifo_item.rd_en}]++;
```

| wr_en / rd_en | 배열 위치 | 의미 |
| --- | ---: | --- |
| 00 | 0 | 대기 |
| 01 | 1 | 읽기 요청 |
| 10 | 2 | 쓰기 요청 |
| 11 | 3 | 동시 요청 |

이것은 요청이 관찰된 횟수이며, 데이터 정확성을 판단하지 않습니다. 요청이 full/empty에서 실제 수락됐는지에 따른 coverage까지 구분하지 않습니다. monitor가 매 클럭 전송하므로 driver의 쉬는 클럭도 idle로 집계됩니다. 지금 sequence에는 동시 요청이 없으니 simultaneous=0이 정상입니다. 모든 항목을 채우라는 통과 조건도 넣지 않았습니다.

## 기존 코드에서 필요한 연결 변경

- fifo_env: 기존 agt에 scb와 cov를 추가 생성하고 analysis port를 연결했습니다.
- fifo_pkg: scoreboard와 coverage 파일 두 개를 env 앞에서 포함합니다.
- fifo_test: 기존 seq.start() 다음에 상승 에지 한 번을 기다립니다. 마지막 item_done과 monitor.write가 같은 하강 에지에 실행될 수 있어, 관찰값 비교가 끝나기 전에 objection을 내리지 않도록 한 것입니다.

```systemverilog
seq.start(env.agt.sqr);
@(posedge env.agt.drv.vif.clk);
phase.drop_objection(this);
```

## 유지한 기본 동작

- driver: get_next_item → drive_item → item_done, negedge 구동·다음 negedge enable 해제
- monitor: posedge 요청·full/empty 저장 → negedge rdata 저장 → analysis 전송
- sequence: write/read 자식 sequence를 기존 상위 sequence에서 순서대로 start
- top: 초기 reset·clock·DUT·config DB 연결

초기 reset 후에만 요청을 실행합니다. 동작 중 reset을 추가하면 현재 scoreboard queue도 함께 초기화하는 처리가 필요하므로, 그것은 기본 구조를 이해한 다음 확장합니다.

## 로그에서 읽을 순서

```text
[SCB] PUSH data=000000a5 queue_size=1
[SCB] MATCH expected=000000a5 actual=000000a5
[SCB] writes=1 comparisons=1 remaining=0
[COV] idle=... read=1 write=1 simultaneous=0
```

coverage와 scoreboard의 report 로그 출력 순서는 달라질 수 있습니다. 실제 실행 수치는 실행결과.md에 기록합니다.
